# Byte Buddy

Personal, dependency-free canvas extension combining IT-ticket progress with verified GitHub contributions. One companion, overall XP total, and level; separate ticket/GitHub accounting and analytics.

## Install and update

Install from the Copilot app (**Install extension from gist**) using the install gist, then restart Copilot. Installs and updates come from that gist; the repo is the source of truth.

Byte Buddy checks the gist for a newer `version.json` when it opens and every 6 hours; **Settings → Check for updates** forces a check. A banner offers **Install update**, which replaces only code and UI files in place. `artifacts/` (your save) is never touched. Restart Copilot afterwards. Agents can use the `check_for_updates` and `install_update` (requires `confirm: true`) actions.

To publish: bump `version.json`, commit, and push to `main`. The **Publish to install gist** workflow runs the tests and updates the gist (tests are not published). Pushes that do not bump the version publish nothing. One-time setup: add a repository secret `GIST_TOKEN` containing a personal access token with the `gist` scope.

## Connections

Tickets always come from the Information Technology MCP server (read-only `search_tickets` for the configured user); there is no ticket-source selection. Open **Connections** to enable GitHub and choose organizations/repositories. Existing unrestricted GitHub settings retain their history but pause new imports until an explicit scope is saved.

## Activation and GitHub access

Reload the Byte Buddy extension through the app if that action is available; otherwise restart the Copilot app and reopen Byte Buddy. Refreshing the embedded web page alone does not reload the extension's server modules. The new runtime registers `get_github_progress`, `sync_github_activity`, and `set_github_settings` canvas actions.

GitHub reads use the locally installed, authenticated `gh` CLI: REST GET for identity/search discovery and bulk GraphQL POST queries for read-only PR evidence. Credentials stay with `gh`; they are not persisted in progression records. The source verifies a human account's numeric GitHub ID and host, pins that identity, and refuses to mix accounts. Sign back into the originally linked account if it changes. Repository visibility is limited to the active account's permissions/SSO authorization.

**GitHub sync is manual-only.** Click Sync GitHub to start or resume history retrieval. Opening the canvas, changing settings, polling, elapsed retry deadlines and restarting never initiate GitHub requests. Connections accepts organization names and `owner/repository` names as a union, restricted to the linked account's own attributable activity. Empty scope or disabling GitHub pauses imports; there is no all-contributions mode. Scope changes reset discovery checkpoints while preserving rate-limit/backoff deadlines and all earned career XP, rewards and evolution credits. Analytics show selected-scope evidence; career progression continues to include retained earned history. With no selection, retained history remains viewable and labeled as such. No new rewards are settled by editing settings alone.

Historical discovery is paginated, partitions searches around GitHub's 1,000-result ceiling, and saves an opaque resumable cursor. A manually started continuous import checkpoints every 40 PRs and retrieves evidence in serial bulk groups, not four or more REST calls per PR. Review, thread-comment and file connection overflow is explicitly paginated. Full file counts are verified before retaining only test/documentation paths needed for existing rewards; unrelated per-file rows are not persisted. Cached data remains visible throughout. Manual refresh starts or joins the same import; there is no post-completion cooldown or overlapping scan, and HTTP/canvas actions return immediately while SSE reports progress.

Quota preflights, REST remaining/reset headers and GraphQL cost/remaining/reset metadata proactively preserve safety reserves. Searches and serial bulk queries are paced separately to reduce secondary-limit pressure. Shared quotas and GitHub's dynamic secondary limits cannot be guaranteed away: actual limits and Retry-After/reset deadlines checkpoint and pause requests without hammering the API. Deadlines survive restarts; click Sync manually after a pause expires. Stalled discovery/errors back off for five minutes. An individual failed PR does not block healthy remaining work: transient evidence failures retry after five/ten minutes, with at most three attempts per unchanged PR; permission/missing-resource failures stop immediately. Unavailable evidence remains explicitly unknown and is retried if GitHub reports that PR updated. Import completion means all discoverable work was attempted, not that inaccessible evidence was fabricated. Discovery permission failures are reported separately in warnings. Status shows processed/pending/unavailable counts and distinguishes rate-limit pauses from error retries. A completed cursor retains the original discovery watermark so incremental overlap catches updates during a long import. Unchanged closed details are reused from the cache (not ETags); open PRs are refreshed. Closing the app stops updates; the next manual click resumes durable checkpoints without resetting progression.

## Playing with your buddy

Only the painted buddy sprite responds to pointer care; clicking the empty room or shadow does nothing. Click/tap to pet (or wake a sleeping buddy). Hold still on the sprite for **one second** to pick it up: a gold progress ring fills during the hold, then a glow and grabbing cursor indicate pickup. Drag with mouse, pen or touch and release to drop/throw. Movement before pickup cancels the press; Escape, pointer cancellation, focus loss and hiding the window cancel safely. Focus the room and press Enter/Space to pet/wake using the keyboard.

While held, the buddy rotates and scales around the exact painted pixel you grabbed, keeping that point under the pointer unless a room boundary intervenes. Grabbing above versus below the body changes the sway direction. It sways like a damped pendulum around your grip: its body lags behind horizontal dragging with a stronger lean at higher speeds, responds immediately to direction changes with a bounded angular impulse, and settles when you stop. The angle is bounded and the rotated sprite stays inside the room; reduced-motion mode disables sway. Throws have capped velocity, gravity, air drag, floor friction and bounces within the room. A hard side-wall hit squashes the sprite, which recovers and returns toward home. Gentle pickup/drop is free; a fast fling or hard wall splat costs **5 affection**, at most once per throw and **once per 5 seconds**, enforced and persisted by the backend across reloads/restarts. Affection never falls below zero, inactivity does not undo penalties, and abuse never awards care counts or XP. Reduced-motion mode keeps pickup/drag but skips ballistic/splat animation. The interaction uses a temporary animation-frame loop only while pressing/dragging/throwing, does not rebuild analytics, and saves only one small hot-state mutation for an eligible penalty—not every movement/impact.

The pet interaction update changes backend modules and static routing, so **restart Copilot** to activate it fully; refreshing the iframe alone is not sufficient.

## XP economy

`economy.mjs` configures GitHub reward weights, a contribution multiplier, thresholds, caps, challenge rewards and level requirements. The multiplier is applied before per-day caps; challenge rewards have their own configured values. Existing ticket rewards remain in `catalog.mjs`; saved ticket XP is retained rather than repriced.

| Contribution | Default XP |
| --- | ---: |
| Legitimate PR opened (nonempty description) | 8 |
| Meaningful authored PR merged | 90 |
| Meaningful review of another human's PR | 38 |
| Constructive review / explicitly acknowledged helpful feedback | 19 / 19 |
| Verified clean merge / first-pass approval | 23 / 11 |
| Focused / substantial contribution | 15 / 23 |
| Readiness / timely substantive review / turnaround | 4 / 8 / 8 |
| Documentation / test-file contribution | 8 / 11 |

A meaningful PR currently requires at least 5 changed lines and a changed file; drafts do not qualify. Focused PRs have at most 400 changed lines and 10 files. Substantial work requires 200–1,500 changed lines, at least 3 files and test-path evidence with complete file context; line volume is not rewarded proportionally. File-based bonuses recognize relevant paths, not semantic proof of better tests or documentation. Turnaround requires reviewed/approved work of at least 50 lines, at least one hour elapsed, and at most 72 hours (168 for substantial work). Responsiveness requires substantive feedback within 24 hours, not an empty quick approval.

Per-PR contribution keys prevent repeat payouts. All cached events are ordered by occurrence time and stable key before daily caps: opened 23, merged 450, reviewed 150, other contribution bonuses 113, total contribution XP 638 per UTC day. Challenge XP is separate from these caps, keyed once per challenge occurrence. Late historical backfill can reallocate capped events but converges to the same total regardless of page/import order. Ordinary comments, bot reviews and self-reviews earn no review XP. Closed-unmerged PRs never earn merge rewards. Helpful feedback requires a linked, later acknowledgment from the actual PR author; reactions alone do not qualify.

The approved rebalance retains **75% of prior configured GitHub rewards and daily caps**, rounded per award to whole XP, including existing eligible GitHub challenge bonuses. Reloading the backend replays cached contributions quietly without fetching GitHub again. Because rounding, caps and newly added challenge eligibility are applied event-by-event, the displayed total is not necessarily exactly 75% of its former value. Ticket awards and permanent unlocks are preserved; overall level can decrease. Repeating the replay does not duplicate XP, challenge rewards or treats.

**Own PRs merged** counts authored PRs merged by anyone. **PRs merged by you** counts verified merger actions, including merging another person's PR. A self-merged PR can appear in both role counts but earns authored-merge XP only once; merger-role events award no extra XP and do not become authored quality samples. Missing merger identity remains unknown, never inferred from the author. The next manual sync backfills available merger evidence in the existing bulk pipeline and discovers merge actions within the existing repository scope. Cached history is immediately usable before that sync; missing attribution is disclosed.

Level cost is `360 + 225 × (level − 1)`, increased from the original `300 + 180 × (level − 1)` to accommodate the second earning source. Normal merges are comparable to a normal ticket, while review/opening rewards are smaller and capped. Legacy ticket challenge rewards are unchanged; this is not a retroactive ticket rebalance.

## Buddy types and manual evolutions

Customize has **Evolution** and **Accessories** subtabs, styled and keyboard-navigable like Progress: Left/Right switches tabs, Home selects the first and End selects the last. Selection is retained while navigating sections or receiving state updates, until the iframe reloads. Evolution contains buddy types, stages and wallet controls; Accessories contains the existing cosmetic categories. The pet room spans the same full content width as the controls at every screen size, retaining its 4:3 aspect ratio. These frontend changes activate with an iframe refresh.

Evolution starts with five freely available companions: **Robot, Cat, Dog, Dragon and Slime**, each with five distinct pixel-art stages. Dragons have rounded heads and snouts, tapered bellies, short haunches, curled tails and growing bat-style wings with finger bones, scalloped membranes and layered shading; existing accessory anchors and painted-pixel interaction stay aligned. Switching species is free. Name, affection, care and cosmetics are shared; purchased stages and the displayed stage are tracked separately for each species. You can display any previously purchased stage without losing ownership or receiving a refund. Levels no longer evolve your buddy automatically.

The **Style** accessory applies to every species and all five stages in the room, Style previews and evolution gallery. **Classic** preserves the original artwork (including the redesigned Dragon), **Retro Boxy** uses broader, squatter heads and squared bodies, and **Bubble** uses puffier heads and rounded bodies. Species features, accessory anchors and painted-pixel pickup targets follow the selected geometry; the Robot's legacy styles are unchanged. This artwork update needs only an iframe refresh, not a Copilot restart.

All buddies spend from **one shared evolution-credit wallet**. Each new lifetime XP point contributes one credit; spending never lowers lifetime XP, overall level, achievements or cosmetic unlocks. Upgrade prices for stages 2–5 are **5,000 / 15,000 / 30,000 / 50,000 credits**, configured in `economy.mjs`. Each purchase unlocks the next stage in order, immediately selects it and celebrates that species' evolution. Starters and upgrades have no level requirement. The wallet is separate from treats.

The version-4 migration resets the former automatically evolved Robot to stage 1, retains all earned XP and credits the wallet with **current lifetime XP plus the equivalent former evolution cost**. The fixed legacy bonus for previous stages 1–5 is **0 / 5,000 / 20,000 / 50,000 / 100,000 credits**; it is awarded once, not again after reset/restart. Existing award IDs, unlocks, appearance, name and care remain intact. Live and demo evolution wallets stay isolated.

**Reset all evolutions** requires confirmation, returns every species to stage 1 and refunds actual outstanding purchases across all species, free of charge. It keeps your active species, XP, level and fixed legacy credit. The wallet always reconciles as `current lifetime XP + legacy credit − outstanding spending`: corrected/reopened evidence can create a deficit but does not revoke purchased stages. New earnings cover that deficit before further upgrades; reopening/reclosing and repeated imports cannot mint credits. Refunds use recorded spending rather than recalculating old purchases at today's prices.

The authenticated `POST /api/evolution` route and `customize_buddy_evolution` canvas action support `switch`, `select`, `upgrade` and `reset`. Requests include the current mode and wallet revision, preventing duplicate/stale purchases or cross-profile spending. Prices and ownership are validated server-side. Each mutation commits only small hot state, reusing unchanged evidence and analytics projections; schema migration checks reconstructed profile parity before publishing. Current-state exports include ownership, spending and legacy credit. The original JSON remains immutable.

**Restart Copilot to activate this feature**: backend modules and the save schema changed; an iframe refresh alone is not sufficient. GitHub sync remains manual-only and ticket access remains read-only.

## Persistence and migration

State version 5 uses dependency-free **hot/cold split JSON**, not SQLite. Live and demo profiles remain separate. GitHub refresh always targets live data, even while demo mode is displayed.

Under `artifacts\<IT-user>\`:
- `buddy.hot.json` is the small authoritative manifest: companion/care state, settings, permanent awards/unlocks and references to cold data. `buddy.hot.backup.json` retains the previous committed manifest.
- `evidence-<live|demo>-<tickets|github>-<generation>.json` files contain complete source evidence. Only a changed source is rewritten; pet, rename and acknowledgement actions never rewrite evidence.
- `projection-<live|demo>-derived-<generation>.json` caches computed progression and range metrics. Raw derived event arrays and duplicate summaries are not persisted. Valid projections let settled startup/Home avoid reading ticket/GitHub evidence entirely. Evidence/range boundaries, calendar rollover and progression-source changes invalidate them; missing/corrupt projections rebuild from evidence.
- Original `buddy.json` and `buddy.backup.json` remain **unmodified**. Initial migration writes new files, checks read-back checksums and canonical full-profile reconstruction parity (including award IDs and unlocks), then atomically publishes the manifest. No progress is reset or GitHub refetched.

Commits write/verify immutable generations before atomically replacing the hot manifest. Known current/previous referenced generations are retained; superseded committed files are cleaned up. Crash-orphaned unreferenced files may remain for manual inspection. Corrupt manifests can recover from the previous manifest; missing/corrupt evidence fails explicitly when accessed. Once split storage exists it never silently falls back to a stale original save. This retains atomic rename/backups, not database transactions, multi-writer coordination or fsync-level durability. Original saves plus previous generations intentionally require additional disk space. Large evidence changes still rewrite the affected cold source and recompute projections; this is not a row-oriented database.

**Current-state rollback:** choose **Export current save** in How it works to download complete legacy-compatible JSON, or call the `export_rollback` canvas action to write `buddy.rollback.json` beside the manifest. The authenticated `GET /api/export` endpoint exposes the same current data; it is an explicit full export, not the compact Home payload. Exports include current progression/evidence, not merely the migration-era original. To roll back, export first, stop Copilot, archive the entire user-artifacts folder without altering its originals, then create a fresh user-artifacts folder containing the current export named `buddy.json` and restore the desired compatible extension version. Do not simply delete split manifests and restart against the old original: that would discard newer progress. Keep the archived folder until the restored XP, awards and unlocks are verified.

Backend module changes require a **Copilot restart**; refreshing the iframe alone does not activate the storage migration. No targeted reload tool was available during this implementation. The temporary SQLite probe code/action has been removed; its successful host result does not mean SQLite is used.

Migration preserves saved ticket awards, unlocks, achievements, appearance and companion state. A one-time, separately displayed **Progress preserved** credit preserves the old level and fractional progress under the slower curve; it is not attributed to tickets or GitHub. No reset is required. Historical GitHub bootstrap quietly records prior achievements/challenges without flooding care rewards. Later completions use existing celebrations, treats and permanent cosmetic unlocks. PR records, rather than synchronization calls, determine contribution XP. Corrected evidence can change GitHub quality eligibility/XP; previously unlocked cosmetics remain unlocked.

The catalog now contains 49 challenges and 74 achievements, including six additional challenges and ten additional achievements for each of tickets and GitHub, plus three usable GitHub cosmetics (GitHub body, reviewer eyes, quality wall). Challenges can be filtered by source, earned status and recurrence/secret type, then sorted by name, XP or completions. Achievements can be filtered by source, unlocked status and grade, then sorted by name, newest earned or grade. Medal pixels and grade pills retain their actual Bronze, Silver, Gold, Platinum or Diamond colors even while locked; locked status remains explicit. Filters survive background updates. Home has three distinct sections in order: pet stats/interaction, GitHub Progress, then Ticket Progress. All use the same outer panel treatment and inset cards. Both progress sections share a renderer for six source-specific stats, a summary, current challenge bars, recent achievement chips and an analytics link. Each has a small header sync button and last-sync status; there is no separate ticket-sync card. Ticket goals use today's existing Hat Trick/High Five/Perfect Ten thresholds, showing the next two unfinished goals (or the completed top goal). Source-specific achievements are not mixed. Evolution lives at the top of Customize. Challenges, Achievements and How it works have their own tabs.

Progress retains Ticket/GitHub sub-tabs, with all-time analytics selected by default. XP charts accumulate earned points rather than plotting daily deltas. PR activity separates opening, authored merges, verified merger actions and reviews; those measures can overlap and are not unique-PR totals. Ticket charts use the complete rewarded ledger (not just the 12 recent tickets), with disjoint normal/Help Desk/critical counts and ticket challenge bonuses dated to completion. Undated legacy XP/tickets remain in lifetime totals and are explicitly excluded from dated charts. Ticket links open the Meyer ticket page. GitHub dates use UTC; ticket dates retain local-time conventions. Ticket range changes update summary statistics, chart observations and recent-ticket links together. Today/week/month and streak statistics are intersected with the selected range using local calendar boundaries (Monday-start weeks); lifetime undated records stay in all-time totals only. PR activity separates authored merges from verified merger actions and reviews.

Click a Progress stat card or chart to open an expanded analytics dialog. Hover or touch a chart to snap the guide to the nearest recorded day and show its date and values in a compact, bounded tooltip. Focus the chart and use arrow keys (or Home/End) for the same accessible day selection; there is no separate observation slider. Switch between lines and bars, with daily data open by default. The dialog retains a snapshot while background updates continue, and Close/Escape restores focus. Summary-only statistics explicitly show related daily activity when no defensible daily series exists; missing evidence remains `—`, not zero. Expanded chart disclosures preserve their state across SSE and periodic re-renders.

## Responsiveness

Only the selected Progress source builds its charts. Chart sections are reused until their source data, selected range or relevant date changes; unrelated care updates do not rebuild historical tables. Open disclosures and keyboard focus survive unchanged updates. Date/number formatters and catalog lookups are reused instead of reconstructed in chart/animation loops. Hidden Home summaries are not redrawn during other tabs' updates. SSE transports tiny change invalidations, not the saved progression file, and coalesces bursts without delaying independent celebration effects.

The server caches derived progression/analytics with mutation and time-aware invalidation, while returning detached view objects so callers cannot corrupt cached results. Repeated polling and runtime-status changes reuse expensive history computations. Immediate atomic saves and backups are retained: earned progress is not held in a deferred write queue. Evidence is complete; the Home transport is deliberately summary-only rather than repeating every analytic timeline.

`GET /api/state` serves compact Home/catalog/status data. Protected `GET /api/analytics` accepts `source=ticket|github`, `range=7|30|90|all`, `offset` and `limit` (default 180, maximum 366). A revision token prevents mixing pages across evidence, mode or date changes; stale requests return 409 and the client reloads. Only the selected Progress source/range is fetched, with no GitHub synchronization triggered by browsing. Cumulative XP retains its earlier-history baseline when a range/page starts mid-history; undated legacy XP is not invented on a chart date. Metrics are source/range cached. Daily tables are created only on disclosure and show 50 rows per page; the chart dialog opens its own bounded daily table by default and retains a stable snapshot. Loading, retry and range-switch races are handled explicitly.

### Current split-storage measurements

A disposable copy of the 18,956,610-byte save (1,599 PRs, 378 tickets), with the original checksum unchanged, measured:

| Operation | Previous monolithic save | Split JSON |
|---|---:|---:|
| Settled startup | 459 ms load only | 19.8 ms including summary |
| Pet mutation, median | 161.7 ms | 13.1 ms |
| Rename, median | 156.9 ms | 21.9 ms |
| Home public JSON | 381,637 bytes | 51,232 bytes |
| Primary bytes written per care/rename | ~18.96 MB | ~29.2 KB |

The live derived projection was 250,845 bytes; raw cold evidence was not loaded for settled Home/care. Fourteen care/rename actions made fourteen immediate writes/backups/renames, totaling 408,765 primary bytes, not fourteen evidence rewrites. Initial verified migration took 2.8 seconds and is intentionally separate from settled startup; a run under transient shared-host load took 8.3 seconds, with correspondingly slower mutations. These are local samples, not latency guarantees. Browser verification measured 836 Home DOM nodes and zero daily rows; selected GitHub Progress had 6,150 nodes versus 12,641 previously and zero collapsed daily rows versus 2,084 eagerly created rows. Opening a disclosure/dialog created only 50 rows each. Home/Progress/modal had no horizontal overflow in a 320px frame; disclosures retained their table nodes across periodic updates. Initial Home rendering was ~40 ms and selected Progress rendering ~8 ms on this fixture; backend/payload and hidden-table savings are the principal improvements, not a claim that every render became faster.

First chart creation measured 25 milliseconds for tickets and 107 milliseconds for GitHub. Its public JSON stayed approximately 634 KB. The expanded progression fixture (1,600 PRs, 250 tickets) retained a 1.8 ms repeated GitHub Progress median, with 100 hover inspections taking 17.1 ms total without rebuilding the dialog. ## Evidence and limitations

- Clean means a complete observed review snapshot, a latest human decision approving the observed PR head, no outstanding changes-requested decision, no historical substantive change request, and no actionable or ambiguous findings. Missing/stale head approval, missing review permissions, bot-only reviews or no review are **unknown**, never clean. The observed head is not an independently reconstructed merge-time snapshot; this is not a defect-free guarantee.
- Actionable findings use conservative text/suggestion markers and recognizable automated-review severity markers, including CodeRabbit. Distinct actionable inline threads are counted once; associated review summaries/decisions are fallback signals, not additional defects. These are observed finding proxies, not semantic defect counts. Ambiguous inline feedback blocks clean bonuses without being invented as a defect.
- Quality rates disclose their assessed denominator and return unavailable values when no eligible evidence exists. Automated findings are normalized per 100 changed lines. Improvement requires two complete, consecutive groups of 5 merges and at least a 20% reduction; pairs do not overlap.
- Review iterations count distinct changes-requested review commits, not every unobservable correction cycle. Readiness is nonempty description plus file context, not a quality assessment of the prose.
- Review-thread comments provide explicit reply linkage; current thread state does not reconstruct historical resolution. No XP is invented for unverified resolution, semantic bug-fix impact, refactoring impact or unblocking a colleague.
- Deleted/inaccessible/private repositories, permissions, search indexing and GitHub's update signals constrain coverage. A changed merged-PR search result triggers review/comment backfill; activity absent from updated-search signals is not guaranteed to be rediscovered. The UI preserves partial/error warnings and cached records rather than reporting complete coverage on failed pages.
- GitHub search cannot enumerate more than 1,000 matching PRs created in the exact same second. If that ceiling is encountered, discovery pauses with a saved cursor and warning instead of claiming complete coverage. Interrupted nested pagination restarts that PR's evidence on the next manual attempt; completed PR checkpoints remain cached.
- Repository titles and links are displayed as data; credentials and raw API payloads are not stored.
